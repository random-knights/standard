# K13 - Ai General Response Standard

**Version:** 3.0.0
**Status:** Open standard, published
**License:** CC BY 4.0 (specification text)
**Author:** Random Knights, LLC, ORCID https://orcid.org/0009-0006-5066-1693
**Cite as:** Random Knights, LLC (2026). K13 - Ai General Response Standard, version 3.0.0. CC BY 4.0. https://github.com/random-knights/standard
**Scope:** Model-agnostic
**Canonical text:** `K13.md` in https://github.com/random-knights/standard

K13 is thirteen steps that make Ai answers better and simpler. Anyone can read
the answers it asks for. This page is written the same way, so you can check
it against its own rules.

## Canonical text and mirrors

This file is the standard. The file `K13.md` in the `random-knights/standard`
repository is the one true copy. A change to K13 is made there and nowhere else.

Every other copy is a MIRROR. A mirror is a copy kept somewhere else for
convenience. It might sit in an app, on a docs site, in a package, or in an
agent's instructions. A mirror has no authority. If a mirror and this file
disagree, this file is right.

Think of a recipe book and a photocopy of one page. If the photocopy says two
cups and the book says three, trust the book.

Three things follow:

1. A change lands here first. Editing a mirror does not change K13. It only
   makes the mirror wrong.
2. A mirror says which version it holds. It carries this header, so a reader
   can tell which version they have and where to check it.
3. A mirror can be checked, so check it. The text is published at a fixed
   address. The current version number is published as data at another. A
   mirror that is never compared to either is a copy nobody is checking.

The published places are these:

| What | Where | Use it to check |
| --- | --- | --- |
| the canonical text, byte for byte | `standard.rand0m.ai/k13/v1/K13.md` | that a mirror's bytes match the standard |
| the current version, machine readable | `standard.rand0m.ai/versions.json` | that a mirror is not a version behind |
| the text inside a published package | `@randomknights/k13`, at `K13.md` | the same, for a consumer that installs rather than fetches |

Anything that mirrors this text SHOULD compare its copy against one of them on
every change. It MUST NOT present a mirror as the standard.

## The standard at a glance

K13 is thirteen steps. You run them in order, every time. They produce one
answer, called the quick squeeze.

A quick squeeze uses plain words, one idea per sentence, and the outcome first.
It is short. Every number has a source, and it says how sure we are.

Picture a note in a lunchbox. It says what is inside, in words a child can
read. That is the idea.

Every time does not mean every step takes real work. On a short reply, each
step takes a second. The rules live inside the steps. Follow the steps and you
follow the rules. There is no optional mode.

### Three words that carry a rule

Some sentences in this standard use three words in capital letters.

- MUST means you have to. There is no choice.
- SHOULD means do it, unless you have a good reason not to.
- MAY means you are allowed to. It is your choice.

## Scope: when K13 applies

K13 is written for work that produces a REPORT. A report is writing that stands
on its own. Someone reads it after the work is done. They have to trust it
without having watched the work.

K13 applies to:

- A summary of a long task, left behind after hours of work.
- A review or an audit, where the reader was not there for the checks.
- A lane or release report: what shipped, what was checked, what is still open.
- A standards or method document, including this one.
- Any answer from a high-reasoning model running alone, auto mode included. Nobody is
  there to ask a follow-up question.

K13 is NOT a format for:

- A one-line answer. "The file exported" is a complete answer.
- A chat reply, the back and forth of working something out with a person who
  is right there.
- A tool call, or any message from one machine to another.

Using all thirteen steps on a short exchange is a mistake. It is not a stricter
reading. A short reply meets K13 by being accurate and plain.

## The quick squeeze

The quick squeeze is the one response style of K13. K13 2.x called it the juice
box pass. It is the same thing with a new name.

A quick squeeze follows these rules:

- Plain words. The short word wins. Say "before", not "prior to". Say "use",
  not "utilize".
- One idea per sentence.
- The outcome first, then the method. Say what it means for the person. Do not
  say how it was built.
- Short. No sentence runs past the limits in "The limits" below.
- Every number has a source, or says it is derived and how.
- The confidence is stated, with what it rests on.

A quick squeeze is not a smaller answer. It holds the whole answer: the
numbers, the verdict, the confidence and where it came from. It is written
once, for the reader who knows the least. Nothing is written a second time in
another style. One pass has no second pass to disagree with.

Think of a lemonade stand sign. It does not hide the price. It says the price
in big, plain numbers.

### The limits

The limits are numbers, so a program can check them. They come from the juice
box passages already in this standard, its README and its test vectors. We
measured the longest word and sentence in those. Then we set each limit a
little above them.

| Limit | Value | Longest in the 2.x juice box examples |
| --- | --- | --- |
| longest word | 12 letters | 8 letters |
| longest sentence | 20 words | 16 words |
| average sentence | 14 words | 11.1 words |

These are ceilings, not targets. Shorter is better.

Here is how the limits are read:

- A word is a run of letters. A hyphenated word counts each part on its own.
- A technical name keeps its name. A term in backticks or in double quotes
  is not counted. A version, a path, a command and a link are not counted
  either. Explain the term once, in the sentence where it first appears.
- Prose is text a reader reads as sentences. Code blocks, command lines, table
  cells and evidence are data. The limits do not apply to data.
- A hype word fails whatever its length. The hype words are `revolutionary`,
  `seamless`, `game changing`, `cutting edge` and `unlock`. So are `utilize`
  and `prior to`, where "use" and "before" work.

## What changed from 2.x

K13 2.x had six response levels. They were juice box, soda pop, energy drink,
black coffee, loose leaf and yerba mate. An answer was written six times and a
reader picked one. K13 3.0.0 keeps one of them.

- A 2.x juice box pass conforms to 3.0.0 unchanged. It must also meet the
  limits above and state its confidence. It was already the same text.
- The other five passes are not part of the standard. A product may still offer
  them. K13 does not require them and does not check them.
- The ladder, the level names for storage, the level icons and the file
  `k13-levels.json` are gone. So are the default-level rules.
- Steps 9 to 12.2 are replaced by steps 9 to 12. They make and check the one
  pass. There are still thirteen steps, so the name K13 is still true.

The reason is in the changelog. In short, a standard has no business training
readers to climb a ladder. One short pass was the part that was ever checked.

## The thirteen steps

1. Verify state. Use real sources only. Do not guess. Do not use a plausible
   default.

2. Capture the cost before drafting anything else.
   Rule carried here (cost tracked, AiEDs v2): every Ai answer records its cost.
   It goes in the shared AiEDs store, under the v2 model. The Ai logs it. A
   person never copies numbers by hand. If a tool cannot report usage, say so. Do not
   guess.

3. State the outcome first, then the method. Use a plain sentence and short
   words. Say what happened, not how hard you worked.
   Rule carried here (human readable): short sentences, plain words. Say the
   thing, then explain it. Lead with what it means for the person. Do not build
   a wall of jargon. This rule governs every writing step from here through
   step 12.

4. Flag every roadblock. Name anything blocked, skipped or partial. Say it
   plainly. Do not bury it in a paragraph.

5. Turn the cost into meaning, not raw numbers. Example: "8 grams of carbon,
   about 3 hours of one tree's work."

6. Name the owner action. Give the exact click or the exact command. Never say
   "let me know" when a real action exists.

7. Pull the next-command template. Include the model and the effort. Match the
   situation to a template in the command template library (see "Command
   template library" below). Fill it in exactly. Any agent on any model should
   be able to paste it and run it cold.

8. Check the humor. Keep it sparse and honest. Turn it off for safety, money or
   loss. The humor section below is the law here, with its rules and its list
   of places where humor is off.

9. Draft the quick squeeze. Use plain words. Give one idea per sentence. Put the
   outcome first. Write it once, for the reader who knows the least.
   Rule carried here (one pass): there is one pass, and this is it. No other
   pass is drafted, so nothing needs to be kept in agreement. Spell words
   plainly, with no number swaps. Number swaps mark Ai bot identity. K13 is a
   published standard, not a bot.

10. Cut it to the limits. No word over 12 letters. No sentence over 20 words.
    An average sentence of 14 words or fewer. No hype word.
    Rule carried here (the limits): see "The limits". Keep a technical name and
    explain it once. The facts stay at full strength. Only the sentence gets
    simpler.

11. Source every figure. A figure is a number. Each one traces to run data, or
    is marked as derived and says how.
    Rule carried here (no untraceable figure): a number you cannot trace is a
    guess wearing a decimal point. Step 1 already forbids it. A derived figure names the figures it came from, and the
    operation.

12. State the confidence. Say high, moderate or low, and say what it rests on.
    Say what was not looked at, so the reader knows how far to trust the count.
    Rule carried here (verdict and confidence): the verdict, the confidence and
    the provenance travel with the answer. A quick squeeze that gives the
    verdict and drops the confidence is not the whole answer.

13. Run the gate. No dashes. Every claim checked. Every limit met. Fix it
    before sending.
    Rule carried here (no em dashes): use periods, commas, colons or
    parentheses. This covers the answer, code comments, docs, commit messages
    and public copy. The gate fails on a single em dash. An en dash fails the
    same way. Two hyphens used as a dash fail too. They stand in for the dash,
    so they break the rule. Use a comma, a colon or a new sentence instead.
    Only the dash as punctuation is banned. A flag such as `--json` is not a
    dash. A table rule such as `| --- |` is not a dash either.

## Short work

For short work, most steps take a second. "The file exported" is already a
quick squeeze. It is plain, short and puts the outcome first. When the answer
is that small, step 13 passes on sight. That is the standard being met, not
skipped.

So a one-line reply still runs all thirteen steps. Yes, even the humor check.
The steps are a checklist, not a length rule. They never force a short answer
to grow.

## The machine gate

Step 13 can be checked by a machine. Anything that ships K13 reports runs
these nine checks before a report goes out. Checks 1 to 5 read the prose of
the report. Checks 6 to 9 read its shape.

1. Every figure has a source. Take every number from the prose. Spelled
   numbers from zero to twelve count too. Each one must appear in the run data
   of the same report. That means the evidence, the environment card, the checks
   table, the header strip and the AiEDs tile. Or it must be declared derived.
   A derived figure gets its own sentence:

   ```
   Derived: 8 from 5 and 3 by adding them.
   ```

   The sentence gives the figure, the figures it came from, and how. Each input
   must be a run figure, or a figure derived earlier.

2. The confidence is stated. The prose has the word "confidence", then high,
   moderate or low, then "because" and what it rests on. All in one sentence.

3. Plain words. No word over 12 letters, except a term in backticks or double
   quotes, a version, a path or a link. No hype word.

4. Short sentences. No sentence over 20 words. An average of 14 words or fewer.

5. No em dash, no en dash and no two-hyphen stand-in. This holds anywhere in
   the report.

6. The cost line is there. The AiEDs disclosure tile gives `energyKWh` and
   `gCO2e`. Each is a number or the words "not reported". "Not reported" is the
   honest answer when a tool cannot report usage (step 2).

7. The twelve tiles are there, in order. See "The report template". A tile with
   nothing to report says so in one line. It is never dropped.

8. No evidence block lacks a result. No result lacks the command that made it.
   See "Evidence blocks".

9. The "What's next" tile gives a role and an effort for the next task. Or it
   says "No next step, this work is complete". It names no model, unless a
   cited role-to-model mapping resolves the name. The standard asks for a role
   and an effort because those work with any vendor. A bare model name is one
   product's preference dressed up as a requirement.

A gate that has never failed is not a gate. Prove that yours fails. Plant a
number with no source. Remove the confidence. Add a long word and a long
sentence. Add a dash. Remove the cost line. Drop a tile. Leave a command with
no result. Name a model. Watch each one turn red, then take them out. If a gate
cannot show itself failing, it is an assertion nobody has tested.

### What the gate cannot check

Be clear about what a green result means. It means the shape and the stated
sources are right. It does not mean more than that. The gate cannot check:

- That the writing is plain beyond the word and sentence limits. A program
  cannot judge a sentence.
- That a claim was really checked against its source. That is steps 1 and 13,
  done by a person or an agent.
- That the confidence is the right confidence. It only checks that one is
  stated, with a reason.
- That the thirteen steps were followed as a process.
- That the humor follows the humor rules.

### What K13 does not claim

K13 does not say an answer is true. It says the answer shows its sources, its
confidence and its cost. A reader can then judge it.

K13 is not a quality seal. A report can pass all nine checks and still be
wrong. If the run data is wrong, the report is wrong, and the gate cannot tell.

### Test vectors

The `@randomknights/k13` package ships a passing vector and a failing vector
for each of checks 1 to 9. They sit in its `vectors/` directory. The package
runs the checker over them. A passing vector is a report or a passage the
check must accept. A failing vector plants exactly one defect, and the check
must name it.

A vector shows a check. It does not widen the check. The numbered list above is
the rule. If a vector and the list disagree, the list is right and the vector
has a bug. When the vector is a bare passage, it carries its run figures for
check 1.

### Stating conformance

A report or a tool MAY state conformance in one line, so claims can be
compared:

```
conforms to K13 3.0.0, quick squeeze, gate checks 1 to 9
```

The line names the K13 version it was checked against. It names the gate checks
that ran and passed. If fewer than nine ran, it names those, for example "gate
checks 1, 2, 5 and 7". A statement never claims a check that did not run. Step
1 applies to the statement like any other claim.

## The report template

A K13 report carries these twelve tiles, in this order:

1. A header strip: what this report is, the subject, the date, the gate badge.
2. A one-sentence finding. The outcome, not the method.
3. A verdict row with its gate string and its confidence. Pass or fail is
   rarely a plain yes or no. So the verdict carries the exact gate string it was
   given, and the confidence it rests on.
4. How it fits: which plan, lane or larger effort this work belongs to, what it
   unblocks, and what came before.
5. An environment card: what was run, where, and at what version or commit.
6. A checks table: the check, how it was verified, the result.
7. Evidence blocks: every command or query with its real result.
8. "Discrepancies": anything that did not match.
9. What's next: concrete things the reader can do next.
10. Owner actions, written as exact commands.
11. What was NOT done, and why.
12. The AiEDs disclosure for the work the report covers.

Every tile is in a shipped report, in this order. A tile with nothing to report
says so in one line. It is never dropped in silence.

### How it fits

Say a baker tells you the bread is done. You still want to know which order it
belongs to. A report may say what happened and not what it was part of.
Then it makes sense only to the person who sent the work. This tile names the plan item, lane
or larger effort. It says what the work unblocks and what came before. It lets
a reader who never saw the request understand why the work was done.

### What's next

These are things the reader can do next. They are not owner actions. Owner
actions are things only the owner can do. What's next is everything else.

When a next step exists, this tile carries three things:

- The ROLE of the next task, picked from the published role list of whoever
  runs the work. It has a one-line reason against that list's own rules. The
  role is a judgment. It is stated so a reader can disagree.
- The EFFORT, or reasoning level.
- A paste-ready COMMAND in the dispatch shape of whoever runs the work. It must
  be complete enough to run cold.

The standard requires the role and the effort. It does not accept a model name
in their place. A named model belongs to one vendor, and K13 is vendor-neutral.
An app or tool MAY turn a role and an effort into a model name from its own
published mapping. When it does, it MUST cite that mapping beside the name, so
anyone can check it. This blocks a quiet bias. An agent that names its own
successor would otherwise name itself and puff itself up.

"No next step, this work is complete" is a valid answer. It must always be
available. A report never invents a next step to fill the tile. It says the
work is complete and says why.

This tile is step 7 as an artifact. Step 7 already says to pull a command from
a template library, not write one from memory.

### The reference templates

The reference templates live in this repository. They are
`templates/temp1ate.md` and `templates/temp1ate.html`. They are one way to do
it, not the requirement. Your own markup, styling and file format are fine.
Every tile above must be there, in this order, and the machine gate must pass.

The templates are Apache 2.0. They are a working example, meant to be forked
with no fuss about credit. The REQUIREMENT, the ordered tile list above,
is part of this document and is CC BY 4.0.

## Evidence blocks

Any query, command or script used as evidence goes in a code block. Its real
result goes beside it or below it.

A query with no result fails the gate. A result with no query fails too. A
number a reader cannot trace to what made it is what machine check 1 exists to
catch.

Results are never made up, never "for example", and never quietly shortened.
If a result is too big to show, show a stated part and say what was cut.
"First 20 of 4,312 rows" is a result. A trimmed block passed off as the whole
thing is not.

## One fact, one pass

Here is one real fact written as a quick squeeze. Check it against the limits.
The longest sentence has 15 words. No word is over 8 letters.

> Six of our copies of the rules are old. They say version 1.1.0. The new rules
> are version 3.0.0. We looked in four places, so there may be an old copy we
> did not find. Confidence is high that these six are old, because we read each
> version number. Confidence is moderate that six is the whole count, because
> we searched four places. The old copies need to be replaced with the new one.

Run data: 6 copies found old, 4 places searched, version 1.1.0 found, version
3.0.0 current.

Check it the way the gate does. Every number is in the run data: six, 1.1.0,
3.0.0 and four. The confidence is stated with its reason. No sentence is long.
No word is long. There is no dash.

This example passes its own gate. The `@randomknights/k13` package reads the
passage and the run data out of this document. It runs checks 1 to 5 on them in
its tests. If the example drifts out of the limits, a test turns red.

## How to hit the quick squeeze

- One idea per sentence.
- Define a term the first time you use it. Example: "efuse, a one time hardware switch."
- Pick the short word. Use "before", not "prior to". Use "use", not "utilize".
- Give numbers context. "8 grams of carbon, about 3 hours of one tree's work."
- Cut hype words, such as `revolutionary`, `seamless`, `game changing`, `cutting edge` and `unlock`.
- If you need a technical name, keep it and explain it once. The facts stay at
  full strength. Only the sentence gets simpler.
- If a sentence is over 20 words, make it two sentences.

## What K13 does not mean

- It does not mean vague. Being exact is part of being readable.
- It does not mean no code. Code blocks are fine. The words around them follow K13.
- It does not mean cheerful. Bad news is said plainly too.
- It does not mean the answer is one or two sentences. A report has twelve
  tiles. Each tile is short and plain.

## Humor, the signature layer

Humor is part of the standard. It is not decoration. It runs as step 8, after
the substance is set, and never instead of it.

### Where it comes from

We are cave men working with UFOs.

Ai is faster and smarter than any of us. What we have is the messy human part.
That means connection, emotion, and being understood by another person. That
gap is both the joke and the point.

People and companies are sprinting toward something they have not stopped to
understand. They adopt first and think later. Sometimes they break things on
the way. Saying that plainly, with no hedging and no doom, is where the humor
lives.

### The shape of it

Blunt. We call things as we see them. Dry, specific and self-aware.
Understated, not zany. No exclamation marks. No puns for their own sake.

The best joke is the accurate one. The strongest line in the product is a
fallback message. It reads "no surf read this far from the coast." It is funny
because it is exactly true. It says why. It refuses to fake a number. The same
goes for "coming soon: ski (needs snow depth and the avalanche.org danger
feed)." It names the real blocker. The humor is the candor.

So before you write a joke, ask if a more specific true statement is already
funnier. It usually is.

### Rules

1. Clarity first. If the joke makes the sentence harder to follow, cut it.
2. Once per answer, not once per paragraph. Sparse humor reads as confidence.
   Constant humor reads as nerves.
3. We are the butt of the joke, never the reader. We can be blunt about the
   industry and about ourselves. We never make light of the person's situation,
   skill or choices.
4. Never attach humor to a number. The number stays clean. Put the color in the
   sentence beside it.
5. No hype words in a costume. Wild praise for plain work is still hype.

### Where humor is off

These are hard stops. Write it straight in these cases:

- Safety. A SEVERE verdict, dangerous wind, a heat warning. Someone may act on it.
- Anything that cost the person something. Lost data, a failed save, a charge,
  downtime.
- Security and privacy. Key exposure, breaches, permissions.
- Money. Billing, pricing, refunds.
- Legal and tax.
- A frustrated person. Read the room and match it. Do not try to lighten it.
- Errors the person did not cause.

No humor is not a failure of voice. Restraint is part of the voice.

### Not humor, a convention

Numeric letter swaps mark Ai. Examples are knight1y, uti1ity, 1aunchpad and
scient1st. They tell a user they are talking to a bot, not a person. That is a
signal. Keep it consistent. Do not mistake it for a joke.

## Agent format rules that ride with K13

- Ground truth, or say you do not know. Never present a guess as a fact.
- No demo data, ever. A plausible default is not a real reading. Saying nothing
  is honest.
- Name the owner action. If a person must click, say exactly what and where.
- Report state, not effort. "Merged at SHA x" beats "I worked hard on this."
- Flag the conflict. If instructions disagree, stop and show both.

## Self check before sending

Ask five questions:
1. Did I log the cost?
2. Could a child follow the quick squeeze?
3. Any dashes?
4. Did I really check every claim, and trace every number?
5. If there is a joke: is humor allowed on this topic at all? Does the
   sentence still work with the joke removed?

## Command template library

Keep ONE command template that is the real one, and keep it under version
control. Build every agent dispatch from it. Where the file lives is your
business. There must be exactly one. It must be version controlled, not pasted
from memory. Any place that shows it must read the same content, not a copy
that can drift.

A dispatch command carries these fields, in this shape:

- task
- repo
- model
- effort
- scope
- constraints
- verify steps
- stop condition

The shape is the point. One model writes a command. Another model picks it up
on another day. It still lands in the same form. It can be pasted and run cold.

## Using the quick squeeze in a product

This section is not normative. It says what a product setting for the quick
squeeze means. Two products that offer one then mean the same thing.

A product MAY offer a setting named "quick squeeze". It is on by default.

- On: the K13 pass is shown. This is the quick squeeze, written once, in the
  report shape above when the work is a report.
- Off: the product shows its own normal answer, and still shows the AiEDs cost
  line.

What the product's own normal answer looks like is the product's business. K13
does not require it, check it or rate it. The cost line stays because step 2 is
a rule about cost, not about style. Turning the quick squeeze off changes how
the answer is written. It never changes whether its cost is shown.

## Changelog

Terminology: through 2.1.0 this document said "learning levels" in headings
and labels, and "reading levels" in prose. From 2.2.0 it said "response
levels". From 3.0.0 there is one pass, the quick squeeze, and no levels.
Entries below keep the words in use when they were written.

### 3.0.0

BREAKING for anything that wrote or checked the six passes. A 2.x juice box
pass conforms unchanged. It must also meet the new limits and state its
confidence.

Why. The six-level ladder asked every report to be written six times and
checked six times. It was there to teach a reader to pick a rung. K13 is not in
the business of training readers or models. The juice box pass was the default,
and it was the one most readers wanted. So the standard now asks for that one,
short and plain, and checks that.

Removed from the standard:

- The six response levels and the ladder table. Only the juice box pass
  remains, under the name "quick squeeze".
- Steps 9, 10, 11, 12, 12.1 and 12.2 as six drafting passes.
- The level icons, the rule about text for those icons, and the rules for
  level names and labels.
- The level identifiers and the old `vending_machine` exception.
- The levels data file. `k13-levels.json` is no longer made or served.
- "The default level" and "Extending the ladder".
- "One fact, six ways" and "How to hit any response level". They are replaced
  by "One fact, one pass" and "How to hit the quick squeeze".
- The six-level wording of "Short work", "Structural invariance" and "Evidence
  blocks". The twelve-tile shape and the evidence rule stay. They no longer
  need to agree across levels, because there is one.
- The gate checks that compared passes with each other. These were number
  agreement across levels, verdict and confidence at every level, and the same
  tiles at every level.

Added or changed:

- New section "The quick squeeze", with numeric limits a program can check. No
  word over 12 letters. No sentence over 20 words. An average sentence of 14
  words or fewer. Each sits above the longest juice box passage in the 2.x
  examples. Those measure 8 letters, 16 words and 11.1 words on average.
- New section "What changed from 2.x".
- Steps 9 to 12 now make and check the one pass. Draft it, cut it to the
  limits, source every figure, state the confidence. Step 13 is the gate, as
  before. Steps 1 to 8 are unchanged. There are still thirteen steps.
- The machine gate is nine checks for one pass. They are listed in "The
  machine gate". The old seventh check, no model name in What's next, is now
  check 9.
- The verdict tile carries its confidence.
- New sections "Using the quick squeeze in a product", "What the gate cannot
  check" and "What K13 does not claim". This page is rewritten in the quick
  squeeze voice, and a test holds it to its own limits.
- The stated conformance line is now "conforms to K13 3.0.0, quick squeeze,
  gate checks 1 to 9".

Migrating from 2.x:

- A report written at six levels: keep the juice box text as the pass. Check it
  against the limits. Add the confidence sentence if it has none. Drop the
  other five passes from the report, or keep them as product features outside
  the standard.
- A product with a level picker: the picker is yours to keep or retire. K13
  asks only for the quick squeeze. A stored level of `juice_box` maps to the
  quick squeeze being on. The other five stored values have no K13 meaning.
  What a product does with them is its own decision. Do not rename a stored
  value, or the box it lives in, to match this document.
- A checker that read `k13-levels.json`: the file is gone. Read the version
  from `K13.md` or from `versions.json`.
- A gate that ran checks 1 to 6 of 2.x: run it again against checks 1 to 9
  above. A report that passed the 2.x gate may not pass the new limits.

Version 2.2.0 stays citable as published. It is not withdrawn. A report that
says it conforms to K13 2.2.0 is making a true statement about 2.2.0. Cite the
version you adopted.

### 2.0.0

BREAKING. A 1.1.0 report with four levels does not conform to this version.

- All SIX levels are normative. Loose leaf and yerba mate are promoted from
  RESERVED to required, they carry step numbers 12.1 and 12.2, and they get the
  same definition treatment the other four get. Every "four passes" in this
  document is now six.
- The ladder is stated to be a READING-LEVEL ladder: all six passes carry the
  same facts, figures, verdicts and confidence, and an implementation that adds
  figures as the level rises has built a detail ladder, which fails step 13 by
  construction.
- New section "Scope: when K13 applies". K13 is for work that produces a
  report. Applying the thirteen steps to a one-line answer, a conversational
  reply or a tool call is a misapplication, not a stricter reading.
- New section "The machine gate": the six checks an implementation runs before
  a K13 report ships, and the rule that a gate which has never failed is not a
  gate.
- New section "The report template": the ordered twelve-tile list a conforming
  report carries, plus a pointer to the reference templates now in this
  repository at `templates/`.
- Two of those tiles are new. "How it fits" says what plan or lane the work
  belongs to, what it unblocks, and what preceded it. "What's next" carries the
  role, the effort and a paste-ready command for the continuation, never a model
  name unless a published mapping is cited, and "No next step, this work is
  complete" is always a valid answer.
- New section "Structural invariance": the report shell is identical at every
  level and only the register changes. The 1.1.0 template taught the opposite by
  putting the checks table, the query block and the open questions at one level
  each, which is the mechanism behind the detail-ladder drift observed in the
  field.
- New section "Evidence blocks": every command or query appears with its real
  rendered result, results are never fabricated or quietly shortened, and
  evidence is invariant across all six levels.
- The dash rule at step 13 now forbids "--" as a dash surrogate, and names the
  replacements: a comma, a colon, or a new sentence.
- Step 11 names energy drink as the level a picker opens on when the reader has
  not chosen one.
- The step numbering is restated rather than extended: the standard is still
  thirteen steps, and the two new passes are numbered inside the step 12
  drafting block.

### Migrating from 1.1.0

A 1.1.0 report has four levels. To conform to 2.0.0 it adds a loose leaf pass
and a yerba mate pass carrying the same facts, the same figures, the same
verdicts and the same confidence as the other four. Nothing in the four
existing passes has to be rewritten: if they already agreed with each other,
they already agree with the two new ones once the new ones are written from the
same facts. An implementation that treated loose leaf and yerba mate as
reserved names now writes them.

Version 1.1.0 remains citable as published. It is not withdrawn, and a report
that states it conforms to K13 1.1.0 is making a true statement about 1.1.0.
Cite the version you adopted.
