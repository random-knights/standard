# Random Knights AiEDs plugin

After every response, this plugin prints an AiEDs receipt: the modeled energy,
carbon, Tree-Time and water of that response and, for coding agents, of the
session so far. The figures are computed on your
machine from the session's real token usage, with the AiEDs reference library,
so they agree with the standard to the number.

The same code is the `aieds` command (`npx @randomknights/aieds`), which also
covers the tools that have no plugin system, and can, if you choose, send each
response's numbers to your own Random Knights account (see
[Send receipts to your account](#send-receipts-to-your-account)). Nothing is
sent until you ask for it.

## What is new

Plugin 0.7.0 (installed copies pick up everything in this list, including the
two receipt items that were drafts under 0.6.0):

- **K13 rules at session start.** A SessionStart hook, in Claude Code and in
  Codex, adds the thirteen K13 steps and the K13 voice line to the model's
  context, about 150 words, before the first prompt. It reads no file, makes no
  network call and never blocks. The text is `hooks/k13-session.mjs`, and
  `test/k13-session.test.mjs` holds it to `K13.md` in this repository: the same
  version, thirteen steps in order, the same limits. Codex users trust it in
  /hooks, as they do the Stop hook.
- **A shorter, plainer receipt.** Three lines, one per scope: this response,
  this session and your account. Each has energy, carbon, water and tree-time
  at one significant figure with a tilde. Then one line comparing your account
  total to phone charges and kilometers of driving, and one line of basis in
  plain words. Cached text is counted as free on the receipt (PROPOSED

  ratified figure; `aieds explain` prints both counts.
- **Your account total, kept on this computer.** A running total per user in
  your config folder, one entry per session so a session is never counted
  twice. `/random-knights:aieds-account` shows it and
  `/random-knights:aieds-account-reset` starts it again from zero. It is never
  sent anywhere.

Plugin 0.6.0:

- **A readable receipt.** The receipt is now up to four lines instead of one
  paragraph: this response and the session on separate lines, units scaled to
  read between 1 and 999, two significant figures while confidence is low, water
  as a tilde figure, a tokens line only when the cache explains a large input,
  and one basis line in place of three repeated sentences. The water range, the
  full disclaimers and the unrounded figures moved to `aieds explain`. No factor
  or computed value changed; this is presentation only.

Plugin 0.5.0 (the npm package `@randomknights/aieds` carries the same code as
its `aieds` command, versioned with the methodology):

  submit | delete` (see [Contribute to the community totals](#contribute-to-the-community-totals)).
  Off by default. Nothing is sent, and no file is written, until you run
  `aieds contribute on` and agree to the consent text. What it sends is one

  production yet: when the service answers that it is unavailable, the command
  prints "Community totals are not available yet." Keep contributing off until
  the service is announced.
- **Modeled water estimate.** The receipt gains a water line, always a range

- **Copilot CLI reader.** `aieds install copilot` adds an `agentStop` hook that

## Install

In a Claude Code session:

```text
/plugin marketplace add Random-Knights/Standard
/plugin install random-knights@standard
```

Or from a shell:

```bash
claude plugin marketplace add Random-Knights/Standard
claude plugin install random-knights@standard
```

Node.js 20 or newer must be on your PATH (`node --version`). Claude Code does
not ship Node, and the hook is a small Node script with no dependencies. On
Windows, the install and the hook run from PowerShell or cmd the same way.

`npx @randomknights/aieds install claude` prints these two commands and checks
whether the plugin is listed; it changes nothing itself.

## What you will see

After each response, this:

```text
this response                  ~50 Wh, ~20 g CO2e, ~0.2 L water, ~8 h tree-time
this session                   ~60 Wh, ~30 g CO2e, ~0.3 L water, ~10 h tree-time
your account on this computer  ~100 Wh, ~50 g CO2e, ~0.6 L water, ~20 h tree-time

Your account so far is about 10 phone charges, or about 300 m of driving.

A guess, not a measurement. Cached text counted as free.
```

The numbers above come from a sample session file, not a measurement.

- Three scopes, one line each. "This response" is the whole turn, every model
  call the agent made to answer you. "Your account" is your own running total
  (see [Your account total](#your-account-total)).
- Every figure has one significant figure and a tilde, because the confidence is
  low and a second figure would claim a precision the estimate does not have.
- Units step up so the number stays small: Wh, kWh, MWh; g, kg, t CO2e; mL, then
  L from 100 mL; minutes, hours, days, years. Large numbers get thousands
  separators.
- Cached text counts as free on the receipt. Plain input, text written to the
  cache and output are charged at the model's coefficient with the data center
  overhead (PUE). The ratified count charges cache reads at the full input
  rate (methodology 2.4.1), which in a long agent session is most of the
  figure. The real figure is very likely between the two; the receipt shows the
  floor. This counting rule is a PROPOSAL (methodology section 2.7), not yet
  ratified.
- The comparisons line is computed from your account total only, with the
  standard's own constants: 12 Wh per phone charge and 170 g CO2e per km of
  driving. It is an educational comparison, not a claim about what was used.
- The last line is the basis. A model with no published figure adds one more
  sentence saying so. The three required sentences (energy and carbon are
  modeled estimates, Tree-Time and equivalents are educational comparisons,
  water is a modeled estimate), the water range, the unrounded figures, both
  counts and the full token counts are in `aieds explain`.
- A receipt from a wrapper (`aieds ollama`, `chat-completion`, `usage`) or the
  Copilot CLI has the response line and the basis line only: there is no
  session to total.

### Your account total

The account line is a running total for you, kept in a file in your user config
folder (`account-total.json`, next to the files described under
[Network and privacy](#network-and-privacy)). It holds one entry per session,
keyed by a hash of the session id, with that session's four totals. A session
that is recorded again replaces its own entry, so it is never counted twice. The
file holds numbers and hashes only: no prompt, reply, model name, folder or
session id. Nothing sends it anywhere, and it never includes another user's
data: it lives in your own profile folder.

Until you link an account with `aieds connect`, the line reads "your account on
this computer". After you connect it reads "your account". The total itself is
still the one on this computer; it is not combined across devices.

| Command | What it does |
| ------- | ------------ |
| `/random-knights:aieds-account` (or `aieds account`) | Shows the total, its comparisons, how many sessions it counts and where the file is. |
| `/random-knights:aieds-account-reset` (or `aieds account reset`) | Starts the total again from zero. A session still running counts only what it uses after the reset. |

### The water line

The receipt shows water as a tilde figure on each scope line (for example
`~1.8 L water`); the range, in `aieds explain`, is described here. It is modeled from the
same energy (AiEDs 2.5.0, methodology section 2.6): consumed water, not
withdrawn water, for cooling at the data center and for the power plants that
supply it. It is always a range in `aieds explain`, from a low case to a high case, and its
confidence is low. The grid part is a US average, whatever region served the
work. It covers inference only, and it is not a measure of scarcity: a liter in
a wet place and a dry place count the same here. The teaspoon is an educational
comparison of 5 mL. Above 250 teaspoons the line shows liters instead. The
coefficients come from the Lawrence Berkeley National Laboratory 2024 United
States Data Center Energy Usage Report (LBNL-2001637); the plugin cites it and
does not copy it.

Two commands show more, on demand:

| Command | What it prints |
| ------- | -------------- |
| `/random-knights:aieds` | The receipt for this session so far, the same receipt. `/aieds` also works when no other command has that name. |
| `/random-knights:aieds-explain` | The formulas, the constants and the source of every coefficient, read from the bundled library, then this session's receipt unrounded: both counts (cache reads charged and cache reads free), the water range, the full token counts and the three disclaimers. |
| `/random-knights:aieds-account` | Your account total on this computer. |
| `/random-knights:aieds-account-reset` | Starts your account total again from zero. |

## What is measured

Tokens only. For each model call the plugin reads the model name, an id and the
token counters the tool itself recorded: input, cache write, cache read and
output. It never reads a prompt or a response into a figure, never stores one
and never prints one.

How the figures are built (AiEDs methodology section 2.4):

```text
energyWh = inTok/1000 * whPer1kIn + outTok/1000 * whPer1kOut
energyWh = energyWh * pue
gCO2e    = energyWh/1000 * 429
treeTimeMinutes = gCO2e / 21000 * 525600
```

Cache-write and cache-read tokens are input, and they are charged at the full
input rate (methodology section 2.4.1). That is a stated conservative bias, not a
measurement: a cache read almost certainly costs less than recomputing the
prefill it replaces, and no provider publishes the ratio. Coding-agent sessions
carry a large cached context, so the figures run high for that reason, in a
known direction. The short receipt shown after each response takes the other
side of that gap: it counts cache reads as free (a proposal, methodology
section 2.7), so it runs low. `aieds explain` prints both. The local log and the
optional sync keep the ratified count.

For models in the coefficient table the receipt uses that model's coefficient.
Claude models carry a class estimate, because no per-query figure is published
by the model's vendor. A model that is not in the table gets the frontier-class
estimate and the receipt says so. Confidence is always low: a token count is a
proxy for energy, not a measurement of it.

## Network and privacy

Nothing leaves your machine unless you run `aieds connect` (your own reports)
or `aieds contribute on` (community totals). Each has its own consent, its own
token file, and is off by default. With neither, the plugin makes no network
call. Set `AIEDS_SYNC=off` or `AIEDS_CONTRIBUTE=off` to block either.

Until you run `aieds connect` or `aieds contribute on`:

- Nothing leaves your computer. The plugin and the `aieds` command make no
  network request, with one exception you ask for: `aieds ollama` talks to the
  Ollama server you name (by default on your own machine).
- No telemetry. Nothing is sent to Random Knights or anyone else.
- One file is written: your account total (`account-total.json` in your user
  config folder: four numbers and a hash per session, see
  [Your account total](#your-account-total)). No code sends it anywhere. The
  other exceptions are a local log you turn on yourself (below), and, for the
  Copilot CLI only, a small file of read positions (a byte count and a
  random-looking hash per session, in the same folder) so that each reply gets
  one receipt.
- Prompt and response text are never stored, printed, logged or sent.

After you run `aieds connect`, and only then, each response's receipt goes to
your own account on knightly.engineering. Exactly these allowlisted numbers and
names are sent per response, and nothing else:

```text
rid          a random-looking id so the same response is never counted twice
tsUtc        when it happened
provider     a vendor slug such as anthropic or openai
model        the model id
tokensIn, tokensOut, cacheReadTokens, cacheWriteTokens
tokenSource  reported (the tool gave the counts) or estimated
energyWh, carbonG, waterMl, treeTimeMin   our modeled estimates from the tokens
aiedsModelVersion, aiedsVersion, provenance, confidence   which model made them
agentId      the tool's name, for example claude-code
activity, latencyMs   optional; today the plugin sends neither
```

Each batch also names the client (`aieds-cli`, its version, and the tool as
`claude`, `codex`, `copilot`, `grok`, `ollama` or `other`), and the sign-in sent
the device label you typed (by default your computer's name and platform when
you run it in a terminal and press Enter; a generic label when there is no
terminal). There is no field for a prompt, a reply, a file or folder name, a
project, a session id, an API key, an e-mail address or a computer name. The
client checks every receipt against this list before it queues it, and the
service rejects any other field by name.

It is off with `aieds disconnect`, off for one run with `AIEDS_SYNC=off`, and
the data you sent can be deleted on knightly.engineering/reports. See
[Send receipts to your account](#send-receipts-to-your-account).

## Send receipts to your account

This is optional. It needs a free sign-in at knightly.engineering/reports.

```bash
npx @randomknights/aieds connect
```

`connect` prints what will be sent (the consent text) before it does anything,
asks the service for a one-time code, prints a link, and waits while you open
the link signed in and press Approve. `--open` also opens the link in your
browser. The token that comes back is stored in your user config folder and is
never printed:

| System | Where |
| ------ | ----- |
| Windows | `%APPDATA%\random-knights\sync.json` |
| macOS, Linux | `$XDG_CONFIG_HOME/random-knights/sync.json`, else `~/.config/random-knights/sync.json` |

On macOS and Linux the file has mode 0600. Windows has no such mode; the file
sits in your per-user profile folder, whose default permissions already limit it
to you, the system and administrators. `AIEDS_CONFIG_DIR` points the whole
folder somewhere else.

| Command | What it does |
| ------- | ------------ |
| `aieds connect [--label <text>] [--open]` | Device-code sign-in (above). |
| `aieds status` | Whether this device is connected, how many receipts wait, the counters, the last problem. Never prints the token. |
| `aieds flush` | Send the queue now. |
| `aieds disconnect` | Revoke this device's token, delete the token file and the queue. |

After `connect`, the hook adds each response's receipt to a local queue
(`sync-queue.jsonl` in the same folder, numbers only, at most 2,000 entries,
oldest dropped first) and tries to send it at once, with a budget of about two
and a half seconds. The hook never waits longer than that and never fails the
host: if you are offline the receipts stay queued and go out on a later reply,
with a back-off from 5 seconds to 15 minutes. A response the service says is
wrong (a 4xx) is dropped and counted, because sending it again cannot help.
`aieds status` shows the counters.

Every response has its own id, so a replay, a retry, or two devices reporting
the same turn is counted once. The older local log below is a running session
total and is not what is sent.

## Contribute to the community totals

This is optional and off by default. It is separate from `aieds connect`: its
own consent, its own token file (`contribute.json`), its own commands. It needs
the same free sign-in. Nothing is sent until you run `aieds contribute on`,
read the consent text and answer `y`. The exact text is in
[`consent-contribute.txt`](consent-contribute.txt).

| Command | What it does |
| ------- | ------------ |
| `aieds contribute on [--open] [--staging]` | Prints the consent text, asks `[y/N]` (anything but `y` or `yes` means no), then signs you in with a device code. `--open` also opens the link; `--staging` uses the test service. |
| `aieds contribute status` | Whether contributing is on, what waits, what was last sent (totals only), and what the service says. Never prints the token. |
| `aieds contribute preview [--pretty]` | Prints the exact JSON the next upload would send, and sends nothing. Also `--session <id>` or `--transcript <file>` to look at real numbers before you decide (works when contributing is off). |
| `aieds contribute submit` | Sends the closed days now. |
| `aieds contribute delete [--forget]` | Removes numbers not yet added into a monthly total. `--forget` also deletes the record that you agreed, which turns contributing off. |
| `aieds contribute off [--delete]` | Stops sending now, tells the service, deletes the token file and the queue. |

Order matters when you want both: `off` removes the token that `delete` needs,
so run `delete` first, or use `off --delete`, which does that.

While contributing is on, each response's numbers are added to a local queue
(`contribute-queue.jsonl` in the same folder as the token file: the UTC day,
the names and the counts above, no time of day and no session id, at most 5,000
entries, oldest dropped first). Once a day, after the day closes, the hook sends
the closed days (at most seven days old) in one request, with a budget of about
two and a half seconds and no retries, so it never holds up your tool. If the
service is paused or not available yet, the numbers stay queued, and
`aieds contribute submit` tries again, with at most two retries. The service is
production by default; `AIEDS_COMMUNITY_URL` or `--staging` pick another one
when you turn contributing on, and the token is only ever sent back to that
same service. `AIEDS_CONTRIBUTE=off` blocks every call for that run.

If you turn contributing off while offline, sending stops at once, the queue is
deleted, and the token stays in `contribute.json` only so that the next
`aieds contribute off` can tell the service ("withdraw pending").

Numbers already added into a monthly total cannot be taken out, because the
total no longer holds anything that points to you. For up to 8 days the service
can match your summary to your account, only to stop double counting and to let
you delete it. A total is shown only when at least 50 people are in it, and
counts are rounded.

Once a day, after the day closes, one summary per day, provider, model, tool
and token source is sent. Exactly these fields, and nothing else:

| Field | What it is |
| ----- | ---------- |
| `schema` | the constant `rk-community/1` |
| `day` | the UTC date, no time of day |
| `provider`, `model` | the vendor slug and the model id |
| `host` | the tool, a fixed list such as `claude-code` |
| `tokenSource` | `reported` (the tool gave the counts) or `estimated` |
| `responses` | how many responses that day |
| `tokensIn`, `tokensOut` | sums for the day |
| `cacheReadTokens`, `cacheWriteTokens` | sums for the day, optional |
| `aiedsModelVersion`, `aiedsVersion` | which model version made the numbers |
| `energyWh`, `carbonG`, `waterL`, `treeTimeMin` | our modeled estimates from the tokens; the service recomputes them from the token counts and does not store yours |

There is no field for a prompt, a reply, a file or folder name, a project, a
session id, an API key, a computer name, a location, or the time of any
response.

## Turn receipts off

Set one environment variable in your Claude Code settings
(`~/.claude/settings.json`, or a project's `.claude/settings.json`):

```json
{ "env": { "AIEDS_RECEIPTS": "off" } }
```

Remove the line, or set it to `on`, to turn receipts back on. Any of `off`, `0`,
`false`, `no` or `disabled` turns them off. `AIEDS_SYNC=off` keeps the receipt
but turns the account link off for that process.

To disable the plugin entirely: `claude plugin disable random-knights`.

## Optional local log

Set `AIEDS_RECEIPT_LOG` to a file path and the hook appends one JSON line of
numbers per response. It is off unless you set it. It never contains text.

```json
{ "env": { "AIEDS_RECEIPT_LOG": "/path/you/choose/aieds-receipts.jsonl" } }
```

By default each line is a session running total (session id, model names, token
totals, energy, carbon, Tree-Time, provenance). Add
`AIEDS_RECEIPT_LOG_FORMAT=rk-receipts` and each line is instead one
allowlisted per-response receipt (the exact object that would be sent, with its
own `rid`), which is also the file format for a manual upload.

## Uninstall

```bash
claude plugin uninstall random-knights@standard
claude plugin marketplace remove standard
```

If you connected the device, run `aieds disconnect` first.

## Behavior you can rely on

- The hook never blocks and never crashes the host. On any error (an unreadable
  transcript, a malformed line, a missing file, an unreachable service) it exits
  with code 0. A failure to build a receipt prints nothing.
- The hook reads the final assistant message at Stop time. Claude Code's
  transcript can lag the live conversation, so the hook waits up to two seconds
  for the last message to appear and then uses what is there.
- Usage recorded in subagent transcript files kept outside the session file is
  not counted. Whatever the session transcript itself records is.

## How the library gets here

Claude Code installs a plugin by copying its directory, so this plugin cannot
import `lib/` from the repository. It carries a copy of the two compiled library
files and the factor table under `vendor/`, in the layout the library expects.
`scripts/sync-claude-plugin.mjs` at the repository root is the only writer of
that copy, and CI fails if the copy is not byte-identical to a fresh build of
`lib/`. Nothing in the plugin restates a coefficient. The npm package
`@randomknights/aieds` carries a staged copy of `scripts/` and `vendor/` as its
`aieds` command, so there is one implementation.

by OpenAI as "not a stable interface for hooks and may change over time", so the
reader prints nothing, rather than guesses, when a record is not in the shape it
knows.

Install, from a shell:

```bash
codex plugin marketplace add Random-Knights/Standard
codex plugin add random-knights@standard
```

Then start Codex and run `/hooks` once to review and trust the plugin's Stop
hook. Codex does not run a hook it has not been told to trust, and trust is
tied to the hook's content hash, so an updated plugin asks again.

In an interactive session the receipt shows as a hook line, for example
`Hook | this response   4.8 Wh - 2.1 g CO2e ...` and, on the last line,
`estimate, low confidence - gpt-5.6-terra - AiEDs v2`. `codex exec` runs the same Stop hook
(`hook: Stop Completed`) but prints nothing; if you ran `aieds connect`, the
receipt is still queued and sent. `codex exec` also needs a git repository or
`--skip-git-repo-check` (a Codex rule, not ours).

What is measured: each `token_count` record in the rollout
(`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`). Codex's `input_tokens` already
includes its `cached_input_tokens`, and `output_tokens` already includes
reasoning tokens. Codex's own "tokens used" line is input minus cached plus
output; the receipt counts cached input at the full input rate (methodology
section 2.4.1), as it does everywhere.

The fixture `codex-real-0.162.1.jsonl` holds only the numbers of a real run
(28,142 in, 2,816 cache read, 14 out), and a test checks the receipt equals
Codex's own `last_token_usage` and `total_token_usage`.

## Grok Build

Status: **on demand.** Tested version: Grok Build 1.0.50. The plugin installs
through Grok's own commands:

```bash
grok plugin marketplace add Random-Knights/Standard
grok plugin install random-knights@Standard --trust
```

An interactive 1.0.50 session printed no automatic receipt, so none is claimed.
Ask for it after the session:

```bash
npx @randomknights/aieds receipt --last grok
```

That reads the newest `updates.jsonl` under `GROK_HOME` (default
`~/.grok/sessions`). Other forms: `receipt --transcript <file>` and
`receipt --session <id>`. Add `--sync` to queue the per-response receipts for
your account, or `--format rk-receipts` to write them as a file.

Grok writes each finished prompt's token usage to `updates.jsonl` (one
`turn_completed` record with `inputTokens`, `cachedReadTokens`,
`cacheCreationTokens`, `outputTokens` and a per-model split). On a real 1.0.50
session (grok-4.7: 109,003 in including 80,768 cache read, 1,375 out) the
receipt's counts equal those fields; the fixture `grok-real-1.0.50.jsonl`
holds only those numbers. Earlier findings on 1.0.13 still hold: the plugin hook
was discovered but not run in headless mode, and for a normal turn Grok writes
the `turn_completed` record after its Stop hooks return, so a Stop hook cannot
see its own response. The hook here checks for its own prompt id and prints
nothing when the record is not there, rather than print the previous response's
figures as "this response". When Grok changes either behavior the hook starts
printing receipts without a code change.

## Copilot CLI

Status: **numbers verified; the installed hook has not yet been run inside a
live session.** Tested version: Copilot CLI 1.0.100
(`npm install -g @github/copilot`).

```bash
npx @randomknights/aieds install copilot          # shows a diff, writes nothing
npx @randomknights/aieds install copilot --yes    # writes the hook file
```

That writes one file, `%USERPROFILE%\.copilot\hooks\random-knights.json` on
Windows (`~/.copilot/hooks/` elsewhere, or under `COPILOT_HOME`), with an
`agentStop` command hook in the format Copilot loads at start (version 1, a
`powershell` and a `bash` command, `timeoutSec` 10). It merges into an existing
file without touching your other hooks, makes a `.bak` first, and running it
twice changes nothing. Restart the Copilot CLI afterwards.

How it gets real counts: Copilot's hook payloads carry no usage, but the
`agentStop` payload names the session's own event file (`transcriptPath`,
`~/.copilot/session-state/<id>/events.jsonl`), and that file records one
`session.usage_record` per model call with `inputTokens`, `outputTokens`,
`cacheReadTokens` and `cacheWriteTokens`. `inputTokens` includes both cache
fields. The reader keeps a read position per session, so each reply gets one
receipt from the records added since the last one.

What it reads and what it does not: the same file also holds your messages, the
replies and tool output. The reader scans it as bytes, line by line, and only a
line that contains the literal type `session.usage_record` is decoded; from it
only the model id, the time and four counters are kept. It never parses or
keeps any other line, and skips any line over 256 KB unread. A test plants a
canary string in every kind of text event and checks it never reaches the
output, the queue, the log, the read-position file or the bytes sent.

The fixture `copilot-usage-real.jsonl` holds only the numbers of a real 1.0.100
session, and a test checks the summed records equal Copilot's own
`session.shutdown` totals (71,893 in, 56,132 cache read, 15,752 cache write,
250 out). Copilot's automatic model choice can pick a different model per turn;
each receipt names the model that answered.

## Ollama and Hugging Face

Neither has a hook or plugin mechanism, so there is nothing to install into.
What they have is a chat response that carries its own token counts, and a
command turns those counts into the same receipt. These are wrappers around the
same library, not a plugin install. They need Node.js 20 or newer and nothing
else.

```bash
# Ollama: one chat call, then the reply and its receipt.
npx @randomknights/aieds ollama --model llama3.2:1b "Say hello"
npx @randomknights/aieds ollama --model llama3.2:1b --stream "Say hello"

# Any OpenAI-compatible chat completion saved as JSON, or a saved stream (server-sent
# events or Ollama's newline-delimited JSON), or piped on stdin with "-".
npx @randomknights/aieds chat-completion response.json --provider "Hugging Face"

# Raw counts from anywhere.
npx @randomknights/aieds usage --provider "Hugging Face" --model <model id> --input 1200 --output 300 --cached 800
```

From a clone of this repository, replace `npx @randomknights/aieds` with
`node plugins/random-knights/scripts/aieds.mjs`.

`ollama` accepts `--host <url>` (default: `OLLAMA_HOST`, then
`http://127.0.0.1:11434`), `--num-ctx <n>` to pass a context size through,
`--stream` to stream the reply, and `--no-text` to print only the receipt. The
one network request it makes goes to that host and nowhere else. It reads
`prompt_eval_count` (the whole prompt), `prompt_eval_cached_count` (the part of
it reused from the cache, shown as cache read) and `eval_count` (the output).
With `--stream`, Ollama puts those counts in the final chunk of the stream
(`done: true`); the command reads them there. The fixture
`ollama-stream.ndjson` is a real Ollama 0.40.4 stream (llama3.2:1b, 28 in,
3 out) with the reply text replaced.

For a streamed OpenAI-compatible reply, `chat-completion` needs the final usage
chunk, which the server sends only when the request asked for
`stream_options.include_usage`; without it the command says there are no counts
instead of printing a zero.

Not observed: a response from Hugging Face itself. The account used for testing
had no Inference Providers credits (HTTP 402), so treat the Hugging Face use as
unverified until you run it once with your own credits.

A local model has no per-model coefficient in the table, so the receipt uses the
frontier-class estimate and says so. That figure is an order-of-magnitude
estimate for a data-center model and says nothing about your own hardware.

## Other tools

Other coding agents have their own hook and plugin mechanisms, and their
transcript formats and hook inputs differ, so this plugin makes no claim about a
tool that is not in the table. To use the same numbers elsewhere today, call the
reference library (`@randomknights/aieds`) with the token counts your tool
reports. Google announced that Gemini CLI is being replaced by the Antigravity
CLI; neither has a documented usage field in its hooks, so no reader is shipped.

## Develop and test

```bash
cd lib && npm install && npm run build       # the library
node scripts/sync-claude-plugin.mjs          # refresh vendor/ after a lib change
node scripts/gen-install-table.mjs           # refresh the tables from data/install-providers.json
cd plugins/random-knights && npm test
claude plugin validate ./plugins/random-knights
claude plugin validate .                     # the marketplace
```

To try an unreleased checkout without touching your settings:

```bash
claude --plugin-dir ./plugins/random-knights
```

Bump `version` in `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json` and
`package.json` together when the plugin changes, or installed copies will not
update. `CLIENT_VERSION` in `scripts/syncclient.mjs` is the same number (a test
checks).

The sync tests run the real commands against a fake backend on 127.0.0.1. They
prove the client against the backend's documented contract (connect, queue,
back-off, the 4xx drop, revoke, the time budget, and "no network unless
connected"); they do not prove the deployed service.
